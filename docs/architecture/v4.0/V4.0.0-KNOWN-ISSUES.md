# v4.0.0 known issues (beta launch)

Status of this file: v4.0.0 ships as a beta on 2026-11-12. Everything below is known, accepted for the beta, and queued to be worked on right after the cut.
Each session adds ITS OWN section (AWS, Azure, portal/Nano, tunnel/Mesh). Keep entries short: what happens, where it shows, workaround, owner, test or file to start from.
Format: `ID | impact | what | workaround | where to start`. Impact = S1 (data loss / wrong answer), S2 (feature does not work), S3 (cosmetic / limit).

## GCP + shared gateway / event-bus (session: gcp-night)

What IS verified for the v4.0.0 blocker "one real backend for gateways and event buses": GCP API Gateway, AWS API Gateway v1/v2 and Azure APIM forward to a real
backend with API key / JWT / quota / throttle enforcement on Nano (real Chromium), the offline Docker stack, and Mesh (`gcp-gateway-eventbus-real.mjs` 52/52 on Mesh
with `PUBLIC_URL`). Eventarc retries, backoff and dead-lettering are verified on all three. The items below are what is NOT closed.

| ID | Impact | What | Workaround | Where to start |
|---|---|---|---|---|
| GW-1 | S2 | **Eventarc `httpEndpoint` delivery to a real endpoint does not work on Nano.** Retries, the RETRYING/DEAD_LETTERED states and dead-letter publish work, but `event_bus_engine.http_deliver` uses urllib (fails in Pyodide: `unknown url type: https`) and the bus is synchronous, so it cannot use the `vyomiBackendFetch` bridge. Works on the offline appliance and Mesh. | Use the offline appliance / Mesh for real delivery; on Nano use Pub/Sub or Cloud Run destinations. | `core/event_bus_engine.py` (`http_deliver`), `wasm/gw-bridge.js`, same async-hop pattern as `core/gateway_common.py` `adrive` |
| GW-2 | S2 | **EventBridge and Event Grid retry inline only** (capped at 3 attempts, no background re-delivery); Eventarc has the full engine. | None. | `core/eventbridge_core.py`, `core/azure_eventgrid_core.py` onto the tick-based path used by Eventarc |
| GW-3 | S2 | **Cognito and RS256 JWT verification on Nano fail closed** (JWKS fetch through the bridge is not built; Pyodide has no `cryptography` socket path). A valid RS256 token on Nano gets 401. | Use HMAC/HS256 authorizers on Nano, or the offline appliance / Mesh. | `core/gateway_common.py` `make_rs256_verifier`, `wasm/gw-bridge.js` |
| GW-4 | S3 | **Behaviour change:** an Azure APIM `validate-jwt` policy with an RS256 token whose issuer is discoverable but whose JWKS is unreachable now returns 401 (before: passed with an "unverified" warning). Fails closed on appliance and Mesh. | Make the JWKS reachable. | `core/azure_apim_gateway_core.py` |
| GW-5 | S3 | The async Nano request path skips the `handle()` telemetry recorder (gateway calls on Nano are not counted in request telemetry). | None. | `core/aws_wire_router.py` `_agw_invoke` |
| GW-6 | S3 | Host-style invoke URLs (`<id>.execute-api.*`, `*.gateway.dev`) are routed only when the Host header reaches the app; behind a proxy that rewrites Host use the path forms (`/apigw/...`, `/gcpgw/<id>/...`). | Path-style URLs. | `routes/gateway_eventbus_unified.py` |
| GW-7 | S3 | **Hosted relay (`relay.vyomi.cloud`) `/gw-egress` is only tested under `wrangler dev` (19/19), never on a real Cloudflare deployment.** The `GW_LIMIT` and `EGRESS_LIMIT` rate-limit bindings were not present locally, so those two paths are untested. | Local `vyomi-tunnel gateway-backend <https origin>=<local origin>` always works. | `wasm/relay/worker.js`, `wasm/relay/test-worker-gw-live.mjs` |
| GW-8 | S3 | Chrome shows a Private Network Access prompt for page -> 127.0.0.1 on Nano gateway forwarding (accepted by owner). | Allow the prompt. | `wasm/gw-bridge.js` |
| GW-9 | S3 | **`packaging/tunnel/bin/*` is a hand-edited fork with no generator.** The gateway egress pieces were ported by hand (not published, no version bump); it can drift from `wasm/relay` again. | None. | `packaging/tunnel/bin/vyomi-tunnel.mjs` vs `wasm/relay/local-relay.mjs` |
| GW-10 | S3 | Mesh gateway forwarding needs a backend the Codespace can reach (public https URL); a laptop-local `localhost:3000` backend is only reachable on Nano / offline through the tunnel map. | `ssh -R` / any https tunnel. | `tests/conformance/nightly/gcp-gateway-eventbus-real.mjs` (`PUBLIC_URL`) |
| GW-11 | S3 | Gateway capability entries stay at `limited` (not `full`): LROs complete inline, Eventarc channels/enrollments/pipelines are not modelled, Workflows/GKE/Functions-1st-gen destinations refused. | n/a | `core/capabilities/gcp/apigateway.json`, `eventarc.json` |

## Azure (session: azure-night)

Verified for the beta: v4 console <-> ARM/CLI bi-directional checks (24 services, 145 PASS), Azure VM compute on the live Mesh (UI/API/CLI create, Stop/Start/Deallocate drive the Docker container, `runCommand` runs in the guest, OS disk is a real resource), Azure OpenAI/AI on the Mesh, tunnel recovery 5/5, Nano Azure UI suites 24/26 (the other two are pending items below). The items below are NOT closed.

| ID | Impact | What | Workaround | Where to start |
|---|---|---|---|---|
| AZ-1 | S2 | **Key Vault KEYS are still per space, not per vault** (secrets and certificates are per vault now). Customer-managed-key envelopes (Cosmos, SQL, Service Bus) look keys up by name in the shared store, so scoping keys needs a CMK-aware change. | Use distinct key names across vaults. | `core/azure_keyvault_secrets_core.py` (KvStore), CMK callers in `core/azure_arm_core.py` |
| AZ-2 | S3 | Key Vault ids still carry the request host (`https://<relay-host>/secrets/<name>/<ver>`), not `<vault>.vault.azure.net` (all vaults share one relay host; rewriting would send SDK follow-ups to the internet). A request with no vault in the path/header (native SDK over loopback) uses one shared namespace. | Pass the vault via the `/azure-data/keyvault/<vault>/` path or `x-vyomi-vault`. | `core/wire_ingress.py` (~L601), `core/aws_wire_router.py` |
| AZ-3 | S2 | **Old-console Azure UI suites cannot pass on the v4 headless image**: `offline-ui-azure-metrics`, `-rg-nav`, `-flat-create`, `-resource-group-detail`, `-apim-appinsights` and `nano-ui-azure-flat-create` target `/console/azure` / the legacy `azure-console.html`, which v4 does not serve. `flat-create` is marked `pending` in `suites.json`. | None (test debt, not product). | Retarget to `/v4/azure/` (`wasm/ui-tests/validate-azure-v4-bidirectional.mjs` pattern) or retire; see `tests/conformance/nightly/needs-decision.md` |
| AZ-4 | S3 | SQL `fullyQualifiedDomainName` has no HTTP endpoint on the appliance, so `offline-post-create-azure-sql-fqdn` stays red. | Use the connection info the API returns. | `core/azure_sql_core.py` |
| AZ-5 | S3 | **Mesh admits one running Azure VM at a time** (409 `AllocationFailed`, admission control by design; EC2 about two). A second concurrent run/user is refused. | Stop/delete the first VM. | `server.py` `_mesh_capacity_precheck` |
| AZ-6 | S3 | **Nano (browser) VMs are ARM state only**: powerOff/deallocate change state but there is no container; `runCommand` understands only `echo`, `hostname`, `whoami`, `date`, `uname`, the IMDS token and the Key Vault secret fetch, anything else returns exit 1 "nothing was executed". | Use the Mesh/offline appliance for real compute. | `core/azure_arm_core.py` `_vm_run_command` |
| AZ-7 | S3 | Env-only Azure suites are not run in our CI image: `offline-post-create-azure-event-delivery` (test receiver), `offline-cli-azure` SQL connectionInfo (needs Postgres), job executions (Docker), `*_sdk` tests (no `azure` python module). | Run on the runner stack (`nightly-v4.yml`). | `tests/conformance/nightly/needs-decision.md` |
| AZ-8 | S3 | Production Nano bundle loads Pyodide from the CDN unless the deploy runs `python3 wasm/fetch_pyodide.py` (it flips `wasm/pyodide-source.json` to `local: true`). The portal vendoring (`vendor_to_portal.py`) was not run by this session, so the portal still serves the previous Nano bundle (no Tags-tab, Service Bus endpoint, Function-app wizard `kind` and crawl fixes) until it is. | Run both before deploying the portal. | `wasm/fetch_pyodide.py`, `wasm/vendor_to_portal.py` |
| AZ-9 | S3 | The Azure Nano crawl was last confirmed at 33/34 services clean (before the final Tags/Topic-type fix); the final re-crawl was not confirmed. | Re-run `ui_crawler.mjs --cloud azure` on Nano. | `tests/conformance/hourly/ui_crawler.mjs` |
| AZ-10 | S3 | Mesh pack fixes made in the appliance repo (`codespace/.devcontainer/mesh/`: apt-get IPv4 fallback, llm healthcheck) reach Codespaces only via a sync PR into `vyomi-cloud/sandbox`; PR #3 (DNS fallback, selfcheck) is merged, later pack changes need another `codespace/publish.sh` sync. The DNS fallback itself has only been tested against a fake apt-get, never on a real failing build. | Sync before launching. | `codespace/publish.sh` |
| AZ-11 | S2 | **Per-vault Key Vault on the served ARM was fixed minutes before the cut** (`core/wire_ingress.py` now also looks in `providers/azure_services._state`; before, a vault created over ARM answered `VaultNotFound` on the data plane). Verified only on a local simulator (put/get/other-vault 404/missing 404/delete 404); the published image and the Mesh predate it, so on those Key Vault secrets return 404 until the image is rebuilt. No unit test yet for the provider-state lookup. | Rebuild the image from trunk. | `core/wire_ingress.py` (~L628), add a test with a provider-state vault |
