# v4/iam-identity-audit: identity depth, audit and history, policy checks

Base: `origin/v4/iam-pickers-integ`. Everything below lives in `core/iam_engine` (pure Python) plus thin host adapters, so Mesh (FastAPI) and Nano
(Pyodide) run the same code. `wasm/core` is regenerated by `wasm/build_cores.py`.

## A. Identity depth

### AWS (`core/iam_engine/sts_trust.py`, wired in `core/aws_wire_router.py`, `routes/aws_s3.py`)

REAL
- `AssumeRole`, `AssumeRoleWithWebIdentity`, `AssumeRoleWithSAML`: the role's trust policy is evaluated with the real condition engine (every operator and
  set modifier, `aws:`/`sts:` context keys, `token.actions...:sub`-style provider-qualified keys, explicit deny wins). A `:root` or `*` principal also
  needs an identity-policy allow for IAM callers. Federated trust requires the provider ARN to exist as an OIDC / SAML provider of the space.
- Sessions are stored with expiry, session policy and session tags; `iam_state_adapters.aws_principal` honours expiry and tags, so the temporary
  credentials are evaluated as that role session by the faithful IAM engine.
- IAM Roles Anywhere `CreateSession` (trust anchors, profiles): the role's trust must name `rolesanywhere.amazonaws.com`; certificate fields are parsed from the
  DER; the issuer CN must equal the trust anchor's CN.
- Native wire XML/JSON responses and error codes (`AccessDenied`, `ExpiredTokenException`, `InvalidIdentityToken`, `MalformedPolicyDocument`).
- The unsigned federation calls are routed without a credential scope (`_UNSIGNED_QUERY_ACTION`).

APPROXIMATED (stated, not hidden)
- OIDC ID-token and SAML assertion signatures are NOT verified (no JWKS / IdP egress); the claims are trusted as presented.
- Roles Anywhere does not validate the X.509 chain, CRLs or signature; only issuer CN versus anchor CN, validity window and the fields conditions use.

Changed existing test: `tests/conformance/test_wire_sts_ram_sqladmin_routes.py` used to AssumeRole a role that did not exist and expect success. Real AWS
returns AccessDenied for that, so the test now creates the role first.

### GCP

REAL (already present, verified by `tests/conformance/test_gcp_wif.py`, 27 checks): workload identity pools/providers, workforce pools/providers, CEL-subset
attribute mapping and `attributeCondition`, STS `/v1/token` exchange with RS256 signature verification, expiry, disabled providers. IAM Credentials
(`generateAccessToken`, `signJwt`, ...) and service account keys are covered by `test_gcp_iamcredentials_core.py` (34 checks).
New in this branch: every STS exchange, impersonation call, key creation and IAM admin write is an audit event (section B).

### Azure

REAL
- Managed identities (`core/iam_engine/azure_identity.py`): IMDS `GET /metadata/identity/oauth2/token` (requires `Metadata: true` and `resource`, selects by
  `client_id` / `object_id` / `msi_res_id`), returning real RS256 Entra JWTs with `oid`, `appid`, `idtyp=app`, `xms_mirid`, so RBAC evaluates them as that
  identity. System-assigned identities come from any ARM resource with `identity.type` containing SystemAssigned.
- Federated identity credentials: client-credentials + `client_assertion` exchange checks issuer + subject + audience against the identity's
  `federatedIdentityCredentials`; errors use `AADSTS70021` / `AADSTS700024` / `AADSTS50027`.
- PIM-style schedules (`core/iam_engine/azure_pim.py`): `roleEligibilityScheduleRequests`, `roleAssignmentScheduleRequests`, schedules and instances are ARM
  records of the space. Eligible grants nothing; `SelfActivate` is validated against an eligibility covering scope and role and a maximum of 8 hours,
  creating a time-bound active assignment that `azure_eval._active` honours (it appears at start and disappears at end, no sweeper).
  Error `RoleAssignmentRequestPolicyValidationFailed` with `["ExpirationRule"]` for an over-long activation.

APPROXIMATED
- No PIM approval workflow, MFA, justification or ticket enforcement, notifications or access reviews; the 8 h maximum is fixed.
- Assertion signatures are not verified. `x-vyomi-resource-id` stands in for "which VM is calling" (the real IMDS is link-local to its VM). Managed identities
  are not created as Entra directory objects; the principalId is the ARM one.

## B. Audit and history

`GET /api/iam/<cloud>/events` (and `/events/export?format=csv|json`) on Mesh and Nano. Filters: `name`, `principal`, `resource`, `service`, `outcome`
(`success|denied|error|would_deny`), `readOnly`, `q`, `start`, `end`, `scope=iam|all`, `source=all|events|decisions`, `includeAllowed`, `limit`, `offset`.
Each row has a common envelope plus the cloud's native record under `native`.

| Cloud | Source | Native shape |
|---|---|---|
| AWS | CloudTrail ring (`cloudtrail_events_core`, now enriched with IAM/STS resources, `requestParameters`, `userIdentity` type, `errorCode`, no secrets in `responseElements`) | CloudTrail event |
| GCP | `core/iam_events_core.py`: IAM admin writes (`google.iam.admin.v1.*`), IAM Credentials (impersonation = data-access entry), STS `ExchangeToken` | Cloud Audit Logs LogEntry (`protoPayload.methodName`, `authenticationInfo`, `status`) |
| Azure | `core/iam_events_core.py`: `Microsoft.Authorization` / `ManagedIdentity` writes incl. role assignments, definitions, PIM requests | Activity Log event (`operationName`, `status`, `caller`, `category`) |

Gate decisions (`deny`, `would_deny`) from the decision ring are merged in as `denied` / `would_deny` events. The AWS credential report and the
service-last-accessed pages were already fed by real data (`iam_core._credential_report_csv`, `record_activity` + the decision ring) and are unchanged.

UI (new files, minimal nav lines): AWS `IAM > Event history`, GCP `IAM & Admin > Activity`, Azure subscription `Access control (IAM)` tabs `Activity` and
`Privileged access` (eligible and active assignments, Activate and Deactivate).

APPROXIMATED
- The event ring (5000 entries) is in memory, per interpreter, and not persisted. On Nano it is per Pyodide context: GCP/Azure events recorded in the
  relay worker are not visible to a page-side bridge, and the AWS CloudTrail source is only read when the bridge shares an interpreter with the router.
  This cross-context sharing was NOT verified in a real Nano browser in this branch (Python tests use the Nano state adapter and bridge host only).
- Data-plane calls are not recorded, only IAM-relevant management operations and gate denials.

## C. Policy checks

- `ValidatePolicy` (`access_analyzer.validate_policy`) now also emits, only when the bundled service catalog proves it: `INVALID_ARN_REGION`,
  `UNSUPPORTED_RESOURCE_FOR_ACTION` (resource ARN of another service), `UNSUPPORTED_ACTION_FOR_RESOURCE` (resource type not in the action's catalog resource
  types), `INVALID_CONDITION_KEY` (service-prefixed key missing from the service catalog; `aws:` keys are never flagged), `REDUNDANT_ACTION` (SUGGESTION: duplicate or covered
  by a wildcard in the same statement). Previously: 7 codes. A service with no catalog in the bundle is unverifiable and never flagged.
  Real AA has further `SUGGESTION_*` family codes that the catalogs cannot prove; they are not emitted.
- `analyzeIamPolicy` for GCP: native response is unchanged. With `analysisQuery.options.includeDenyPolicies=true` the response adds `vyomiDenyAnalysis`
  (IAM v2 deny rules under the scope, narrowed by identity, permissions and condition state) and `vyomiDeniedBy` on matching permission accesses. This is a
  Vyomi EXTENSION: the real API does not evaluate deny policies.
- Azure custom role checks: `POST {scope}/providers/Microsoft.Authorization/customRoleChecks` (Vyomi EXTENSION; Azure has no native equivalent). Findings:
  `INVALID_ACTION` (provider catalog proves absence), `DATA_ACTION_IN_ACTIONS`, `NOT_ACTION_NO_EFFECT`, `REDUNDANT_ACTION`, `MISSING_ASSIGNABLE_SCOPES`,
  `WILDCARD_OWNER_EQUIVALENT`, `PRIVILEGE_ESCALATION`; with `reference` a no-new-access PASS/FAIL listing the extra actions.
