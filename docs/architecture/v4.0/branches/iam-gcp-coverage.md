# v4/iam-gcp-coverage

Owner: IAM work package gcp-coverage (Claude) - Started: 2026-11-23 - Base: origin/v4/iam-faithful (1e8f127f5) - Status: ready to merge into v4/iam-faithful

## Purpose
GCP was 0/29 services enforceable and 1,033 Discovery methods were unmapped (a request that maps to no permission is denied while enforcing). Fix the systematic causes, define "enforceable" honestly, add the three services without a slice, model the hierarchy/groups/PAB in the adapters, and make opaque `ya29.` tokens carry an identity.

## Systematic causes fixed
1. **Generic paths** (the biggest one): the generator kept only the plain Discovery `path` (`/v1/{+name}`), which matches any resource and is resolved by guesswork. It now uses `flatPath` (`/v1/projects/{p}/locations/{l}/indexes/{i}`) when Discovery has one. Synthesized-request round trip: 4093/4093 entries.
2. **Renamed / aliased permission families** (`scripts/gen_iam_gcp_methods.py` `ALIASES`, with a reason per row, validated against the catalog so `bad_perms` stays empty): Cloud Build triggers -> `cloudbuild.builds.*`, GitHub Enterprise / Bitbucket configs -> `cloudbuild.integrations.*`, logs-based metrics -> `logging.logMetrics.*`, saved queries -> `logging.queries.*`, SCC notification configs / SHA custom modules, liens, legacy org-policy methods, KMS autokey / KAJ / EKM config, legacy zonal GKE node pools, Artifact Registry project settings and package uploads, Redis token auth users, SLOs, rapidCaches (= anywhereCaches), Service Networking, IAP, Service Usage quotas, Compute Shared VPC (`compute.organizations.*Xpn*`) and resize requests, Firebase Auth (Identity Toolkit admin), Backup and DR data sources / backups / auto-protection bindings, Firestore streaming document methods, Cloud SQL backups -> `cloudsql.backupRuns.*`, Binary Authorization, App Hub.
3. **Wider noun search** (`derive_ext`): raw and scope-stripped nouns (`regionCompositeHealthChecks`, `globalOperations`), camel-joined parent+child nouns (`tensorboards.experiments` -> `tensorboardExperiments`), `<api>.googleapis.com_<noun>.<verb>` permission names (IAM workload identity / workforce / OAuth clients), long-running `operations.*` resolved against the parent resource. All heuristic results carry `f:1` (`fallback_ids`, 1268 ids in total including the earlier verb fallbacks): their permission is the nearest catalog permission of the right resource and verb class, not a verbatim documented mapping. Treat them as best effort; the unmatched list is the honest remainder.
4. **Versions**: the table lists one version per method; requests under `/v1beta1`, `/v1alpha`, `/compute/beta`, `/compute/alpha` now match too (`map_gcp._version_tolerant`), and the resource name drops the version.
5. **Vyomi's own wire** (`/vyomi/gcp/{p}/marketplace/*`, `/vyomi/gcp/{p}/hub/overview`) maps to the permission of the real product it stands for (`consumerprocurement.orders.*`, `commerceoffercatalog.offers.get`, `servicehealth.events.list` + `apphub.applications.list`), listed as `vyomi.*` pseudo methods.

## Enforceable, defined honestly (decision)
Old (GCP): share of the slice's catalog permissions emitted by some REST method. That penalises the catalog for what is not a REST method (console/gcloud/internal-only permissions; `iam` 3053 permissions, 15.9%) and says nothing about whether requests are mapped. New: **Mapped % = share of the service's request surface** (every method of the service's APIs, `service_map.json` `apis` [+ `id_prefixes`], plus Vyomi wire routes) that is mapped: a synthesized request round-trips through `map_gcp.required()` to the method's permission(s) (`testIamPermissions` needs none and counts). Unmatched methods count as NOT mapped. The 90% bar is unchanged. The old number stays as its own column, **Catalog reach %**, with its own floor (`strict_floor`); `tests/conformance/test_iam_gcp_coverage.py` fails if it drops. Floors for the new measure are bumped to today's values.
Limit of the new measure (not hidden): the denominator is the Discovery surface of the service's APIs, not the list of methods the simulator serves. There is no machine-readable served-method list (dedicated cores route by prefix and catch-all; `core/gcp_ext_specs.py` covers 7 APIs only), so a service that serves a small part of its API is measured against the whole API (conservative: it can only under-report). Making the denominator "served methods" needs a served-method registry; not built here.

## New catalog slices (fetched with `gen_iam_catalog.gcp_service`, listed in `GCP_SLUGS`)
`binaryauthorization` (38 permissions), `consumerprocurement` (63) + `commerceoffercatalog` (5) for Marketplace, `servicehealth` (13) + `apphub` (47) for Cloud Hub. There is no `cloudhub` permissions page (the slug returns a page without permissions); Cloud Hub is mapped to the products it aggregates and says so in `service_map.json`. Discovery has no consumer-procurement API, so Marketplace has no Discovery methods: its surface is the Vyomi wire rows.

## Hierarchy, groups, PAB (adapters: `core/iam_state_adapters.py`, `core/iam_state_nano.py`)
`gcp_hierarchy_extras(rm, config)` builds, from the Resource Manager store (`gcp_rm`): project -> folder -> organization parent chain (project number aliases canonicalised to the project id), Cloud Identity groups + memberships (nested groups via the engine's closure), PAB policies + bindings; `apply_hierarchy` merges them into the engine state. A project the store has no record of (the default project is not in `gcp_rm.projects`; `POST /v3/projects` is not served in this build) hangs off the Vyomi-wide organization so org-level bindings and boundaries reach it. When the store holds nothing, the per-space config `gcp_iam_hierarchy` = `{"parents": {"projects/p": "folders/1", "folders/1": "organizations/2"}, "groups": {"group:eng@x": ["user:a@x"]}}` supplies the chain (Mesh: space dict or `STATE`; Nano: `reg["gcp_iam_hierarchy"]`); the store wins on conflict. It is a separate key because `modes.validate` rejects unknown keys in the enforcement document.

## Opaque tokens (Mesh + Nano)
`gcp_iamcredentials_core.generate_access_token` records `sha256(token) -> {email, exp}` in `IamCredentialsStore.tokens` (hash only; persisted with the store slot, capped, expired entries pruned). `iam_state_adapters.gcp_token_principal` resolves a `Bearer ya29.` token from that table or from the WIF STS table (`gcp_sts_tokens`: token -> principal + attributes); precedence: `X-Cloudlearn-Principal` > recorded token > JWT `email` claim > root. A `ya29.` token the simulator never issued (or an expired one) still acts as root. There is no SA-key `jwt-bearer` token endpoint in the appliance (only generateAccessToken and the WIF exchange mint `ya29.` tokens), so nothing else needed recording.

## Tests
`tests/conformance/test_iam_gcp_coverage.py` (pure: mappings, versions, flat paths, Vyomi routes, round trip of every method with a permission, catalog-verbatim, coverage definition + floors, hierarchy/group/PAB state, token recording) and `tests/conformance/test_iam_gcp_hierarchy_e2e.py` (real server + real stores: folder binding inherited via store chain and via config chain, nested/removed group membership, PAB narrowing and widening, `generateAccessToken` token acting as its service account while another SA's token is denied).

## Not done / open

- `testIamPermissions` (no permission needed) and every unmapped request return `[]` from `map_gcp.required`, and `gate.check` treats `[]` as unmapped: with enforcement on and `allowUnmapped=false` it DENIES them. `testIamPermissions` should be allowed (the gate belongs to another WP): `map_gcp.describe()` returns `matched=True` + empty perms for it, which the gate can use.
- Folder/organization allow policies cannot be set through the appliance API (`/v3/folders/{id}:setIamPolicy` and `/v1/organizations/{id}:setIamPolicy` are not served); the e2e writes them into the real IAM store slot. Project create (`POST /v3/projects`) answers 405 here.
- Heuristic (`f:1`) permissions are best effort (see 3); a documented-permission review per row would turn them into verbatim mappings.
- Not run against real SDK traffic or :8099.
