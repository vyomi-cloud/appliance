# Branch v4/iam-opmap-gcp-azure (WP opmap-gcp-azure)

Base: `origin/v4/iam-faithful`. Owns: `core/iam_engine/map_gcp.py`, `core/iam_engine/map_azure.py`, `scripts/gen_iam_gcp_methods.py`, `core/iam_catalog/gcp/_methods.json`, tests `tests/conformance/test_iam_map_{gcp,azure}.py`.

## What it does
- `map_gcp.required(method, url, body=None, host=None) -> [{action, resource, service}]`. Data-driven from Google API Discovery (39 APIs, 4250 methods; `_methods.json`, 800 KB, regenerated by `scripts/gen_iam_gcp_methods.py`). Permission is derived from the method id, validated against the verbatim roles catalog, with a documented override table (reason per entry) and pattern rules. `testIamPermissions` returns `[]` (Google requires no permission). Cloud Storage: JSON + upload + XML API (virtual-host and path style), resource names in the `projects/_/buckets/b/objects/o` convention. Body extras: `iam.serviceAccounts.actAs` for compute/run/functions service-account attachment.
- `map_azure.required(method, path, body=None, host=None, headers=None) -> [{action, resource, data}]`. ARM verb/path rules incl. subscription/RG/deployments/extension resources; data plane for Blob, Queue, Table, Key Vault, Service Bus, Cosmos, App Configuration (host-based or `/azure-data/<svc>/<acct>/...` alias).
- Pure Python (json/re/os), no fastapi/socket; identical code runs on Nano (Pyodide, once vendored with `core/iam_engine` and `iam_catalog/**/_methods.json`) and Mesh.

## Coverage (measured)
- GCP: 3217 / 4250 Discovery methods mapped (75.7%); 634 of those use a heuristic verb fallback (flag `f:1`, ids in `fallback_ids`). Unmatched (1033, listed in `_methods.json.unmatched`) are mostly Vertex AI operations, SCC, workforce pools, logging org/folder saved queries: their permission is not in the roles catalog, so they are NOT emitted (never invented) and fail open as unmapped. `overrides_not_in_catalog` is empty.
- Azure: control-plane round-trip over every catalog action: 7409 / 7653 (96.8%); 89 realistic test requests, 85 emitted IDs verbatim in the catalog, 4 Cosmos SQL data-RBAC IDs outside the catalog (separate role system).

## Wired vs designed (per cloud; Nano and Mesh)
The mappers are PURE functions and are NOT wired into any hook in this branch (the gate/modes/audit/routes belong to enforce-mesh; this WP only provides the mapping they call).
| Cloud | Mapper | Console-adapter path | Native-wire (SDK/CLI) path |
|---|---|---|---|
| GCP | built + tested | designed only: console calls the same `/storage/v1`, `/compute/v1`... REST paths, so `required()` applies unchanged | designed only: input shape = path as seen by `core/middleware.py` (`_gcp_iam_enforcement_response`), which still uses the old `gcp_iam_policy.permission_for_request`; swapping it to `map_gcp.required` is the integrator/gate step |
| Azure | built + tested | designed only (ARM paths identical) | designed only: `_azure_rbac_enforcement_response` still uses namespace-level matching; data-plane aliases `/azure-data/*` are supported by the mapper |
| Nano persistence (IndexedDB settings/audit) | not in scope of this WP | | |

## Not verified / open
- Not run against the live :8099 server or real SDK traffic; test inputs are realistic hand-written requests.
- Cloud Run v1 domain mappings, Vertex operations, SCC etc. unmapped (see above). Compute insert's extra permissions (disks.create, networks.use) are not emitted.
- Storage object `insert` overwrite (also needs `storage.objects.delete`) and XML copy-source are simplified.
- Table MERGE/PUT, queue, Cosmos and Service Bus data-action choices follow Azure docs from memory; confirm when real traffic exists.
- Pyodide vendoring: `wasm/build_cores.py` must also ship `core/iam_catalog/gcp/_methods.json` and azure/gcp catalogs.
