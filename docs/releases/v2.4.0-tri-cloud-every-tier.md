# Vyomi v2.4.0 — "Tri-Cloud, Every Tier"

**Theme:** One conformance contract, best substrate per tier. Bring the GCP + Azure
service parity that Nano now has (in-browser WASM cores) up into Pro/Max on real
backends, unifying every tier on a single shared conformance suite and native-wire
front door — and killing the GCP/Azure implementation drift.

**One-liner (GTM):** *"Everything you can try free in a browser tab (Nano) runs
identically in Pro/Max — the same SDK conformance, now on production-grade
backends. 20 services, 3 clouds, one proven core, native SDKs unchanged."*

Status: PLANNING · Target: v2.4.0 · Owner: —  · Created 2026-07-13

---

## 1. Why this release (the drift, grounded in the code)

The store-seam design (ADR-001) says the *same* substrate-free core runs on any
substrate (Nano in-WASM, Pro/Max real backend, tests). AWS already lives this:
`core/s3_object_core.py`, `dynamodb_core.py`, `kms_core.py`, … are shared by Nano
**and** the Pro/Max server. But GCP/Azure never got there:

| Cloud | Nano (shipped in this cycle) | Pro/Max today | Drift? |
|---|---|---|---|
| AWS | `*_core.py` (in-WASM) | `*_core.py` (MinIO/Vault/NATS/Postgres) | **unified** ✅ |
| GCP | `gcp_storage_core`, `gcp_firestore_core`, `gcp_kms_core`, `gcp_secretmanager_core`, `gcp_pubsub_core`, `gcp_iam_core`, `gcp_cloudsql_core` | `gcp_gcs_store`, `gcp_firestore_emulator`, `gcp_pubsub_emulator`, `providers/gcp_services.py` (bespoke) | **DRIFT** ⚠️ |
| Azure | `azure_blob_core`, `azure_cosmos_core`, `azure_keyvault_secrets_core`, `azure_keyvault_keys_core`, `azure_queue_core` | `core/azure_dataplane`, `providers/azure_services.py` (generic ARM) | **DRIFT** ⚠️ |

Two implementations of "GCP KMS", "Azure Blob", etc. means: bugs fixed in one don't
flow to the other, conformance proven in Nano isn't proven in Pro/Max, and the
marketing claim ("same everywhere") isn't literally true. v2.4.0 fixes that.

**Key nuance:** Pro/Max's GCP path uses the *real Google emulators* (Firestore,
Pub/Sub) — higher fidelity than a hand-built REST core. We do **not** downgrade
those. The unification target is the **conformance contract + wire router**, not
"run the WASM core on the server." Each tier keeps its best substrate; the *same
conformance suite* must pass against all of them.

## 2. Architecture: seam + substrate matrix

```
        native SDK / CLI  ──►  aws_wire_router (ONE native-wire front door, all 3 clouds)
                                     │  routes by SigV4 / X-Amz-Target / GCP path / Azure x-ms-*
                                     ▼
                            conformance CORE (substrate-free wire logic)
                                     │  persists through a STORE SEAM
                     ┌───────────────┼────────────────┐
             InMemory*Store    Backed*Store       EmulatorStore
               (Nano/WASM)     (Pro/Max: MinIO,    (Pro/Max: real
                                Vault, Postgres)    Firestore/PubSub emu)
```

- **The core** owns the wire (request→response), never the substrate.
- **The seam** is the swap point. Today only S3 has all three (`InMemoryObjectStore`,
  the MinIO-mirror hooks). v2.4.0 adds **Backed / Emulator seam implementations** for
  the GCP/Azure services so the shared core runs on real backends in Pro/Max.
- **The wire router** (`core/aws_wire_router.py`) already routes all 3 clouds (built
  this cycle for the Nano relay). v2.4.0 makes the **Pro/Max ingress use the same
  router**, so external SDKs hit identical routing on every tier.
- **The conformance suite** (`tests/conformance/test_*_core.py`) is the contract. It
  runs today against InMemory. v2.4.0 parametrizes it to also run against the
  Backed/Emulator substrates (same asserts, different store) — the anti-drift gate.

| 3 | KMS | AWS | InMemoryKeyStore | Vault Transit | ✅ unified — suite parametrize |

| 9 | GCS | GCP | `gcp_storage_core` | **fake-gcs-server** behind a BackedObjectStore | **PORT**: point core at real GCS backend; retire `gcp_gcs_store` |
| 10 | Firestore | GCP | `gcp_firestore_core` (REST) | **Firestore emulator** (gRPC, higher fidelity) | **CONTRACT-MATCH**: keep emulator; run the shared conformance suite against it; retire bespoke path |
| 11 | Cloud KMS | GCP | `gcp_kms_core` | Vault Transit behind BackedKeyStore | **PORT** |

| 14 | Cloud IAM | GCP | `gcp_iam_core` | in-proc py evaluator | **PORT** (mirror AWS IAM) |
| 15 | Cloud SQL | GCP | `gcp_cloudsql_core` (control) | real Postgres (data) | **PORT** control plane; wire data plane to Postgres |
| 16 | Azure Blob | Azure | `azure_blob_core` | **Azurite** behind BackedObjectStore | **PORT**; retire `azure_dataplane` blob |
| 17 | Cosmos DB | Azure | `azure_cosmos_core` | **Cosmos emulator** or real backend | **CONTRACT-MATCH / PORT** |
| 18 | KV secrets | Azure | `azure_keyvault_secrets_core` | Vault KV behind BackedKvStore | **PORT** |
| 19 | KV keys | Azure | `azure_keyvault_keys_core` (envelope) | **Vault Transit** (real crypto) | **PORT** — closes the KV-keys crypto straggler |
| 20 | Queue / Service Bus | Azure | `azure_queue_core` | Azurite queues / NATS | **PORT** |

Legend — **PORT**: replace the bespoke Pro/Max handler with the shared core + a
Backed seam. **CONTRACT-MATCH**: Pro/Max keeps a superior real emulator; we prove
it satisfies the *same* conformance suite and retire the duplicate wire logic.

**Straggler resolution (free with this release):** Firestore + Pub/Sub gRPC and
KV-keys real crypto — unprovable in Nano — are all satisfied in Pro/Max via the real
emulators + Vault Transit. Nano keeps the REST/envelope cores with documented
limits; the suite proves both meet the contract.

## 4. Workstreams / phases

### Phase 0 — Conformance-suite unification (the anti-drift gate) · ~3d
- Parametrize `tests/conformance/test_*_core.py` over a `SUBSTRATE` fixture:
  `inmemory` (default, host + Pyodide) and `backed` (real backend, host + CI).
- Add a `conftest`/harness that spins the relevant backend (MinIO/Vault/Postgres/
  Azurite/emulators) via the existing compose and injects the Backed store.
- **Exit:** every AWS core's suite is green on *both* substrates. Establishes the
  pattern before any GCP/Azure porting.

### Phase 1 — Proof spike: GCS + Azure Blob on real backends · ~1w
- Implement `BackedObjectStore` (the seam impl that mirrors to fake-gcs-server /
  Azurite / MinIO). Point `gcp_storage_core` + `azure_blob_core` at it in the
  Pro/Max FastAPI adapter.
- Run the shared conformance suite + the **native SDK proof** (`google-cloud-storage`,
  `azure-storage-blob`) against the appliance ingress (not the Nano shim).
- Retire `gcp_gcs_store` and the `azure_dataplane` blob path.
- **Exit:** two services, both clouds, prove "shared core + real backend + native SDK"
  end-to-end in Pro/Max. This de-risks the remaining 15.

### Phase 2 — Storage & data services · ~1.5w
- Cloud SQL (Postgres data plane) + Cosmos (contract-match to a real backend) +
  Firestore (contract-match to the emulator via the suite).
- Deliver `BackedSqlStore` (real Postgres) shared by RDS + Cloud SQL + the RDS Data API.

### Phase 3 — Security services · ~1.5w
- Cloud KMS, GCP Secret Mgr, Azure KV secrets → Vault-backed seams (`BackedKeyStore`,
  `BackedKvStore`).
- **Azure KV keys → Vault Transit** (real asymmetric crypto) — closes the crypto
  straggler; keep the Nano envelope core with a documented note.

### Phase 4 — Messaging & eventing · ~1w
- Pub/Sub (contract-match to the emulator), Azure Queue/Service Bus (Azurite/NATS).
- Confirm SNS→SQS / topic→subscription fan-out holds across substrates.

### Phase 5 — Identity · ~4d
- Cloud IAM core (mirror the AWS IAM py-evaluator) into Pro/Max; unify the RBAC/ARM
  policy evaluation path with the shared evaluator where sensible.

### Phase 6 — Wire-router unification + native-SDK sweep · ~1w
- Make the Pro/Max ingress route through `aws_wire_router` (or a thin server wrapper
  of it), so external SDKs hit identical routing on every tier.
- Run the full native-SDK matrix against the appliance (all the SDKs installed this
  cycle) — the acceptance proof.

### Phase 7 — "Vyomi-in-Vyomi" real-app acceptance · ~1w
- Deploy one real app + managed DB across AWS **and** GCP **and** Azure on a Pro/Max
  appliance, one at a time (the north-star validation). This is the release's
  acceptance test, not a feature.

## 5. Per-tier deliverables

- **Nano (free):** no new services; inherits the *validation dividend* (every core fix
  flows to all tiers via the shared suite). Optional: gRPC-web spike for Firestore/
  Pub-Sub if cheap (else documented REST-only).
- **Pro:** GCP + Azure data planes to AWS parity on **real backends**, native SDKs
  unchanged. The headline value.
- **Max:** same as Pro + the cross-cloud / air-gapped guarantees intact; the
  "Vyomi-in-Vyomi" real-app deploy is a Max showcase.

## 6. Testing & acceptance

1. **Conformance suite** green on `inmemory` (host + Pyodide) **and** `backed`
   (real backend) for all 20 services — the anti-drift gate, enforced in CI.
2. **Native-SDK matrix** (boto3/aws, google-cloud-*, gcloud, azure-*) green against
   the **Pro/Max appliance ingress** — proves "unchanged SDKs" on real backends.
3. **Relay E2E** (Nano) unchanged and still green (regression guard).
4. **Real-app acceptance** ("Vyomi-in-Vyomi"): a real app + managed DB deployed on
   each of the 3 clouds on a live appliance.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Downgrading Pro/Max's real emulators (Firestore/Pub-Sub) by replacing them with REST cores | **CONTRACT-MATCH** strategy: keep the emulator, prove it against the shared suite; only *retire duplicate wire logic*, never the backend |
| Backend footprint / boot time grows (more containers) | Progressive startup (already shipped) + lazy backend boot per service category; Nano stays zero-backend |
| Conformance suite becomes slow with real backends | Split CI: fast `inmemory` on every push, `backed` nightly + pre-release |
| Re-introducing drift later | The parametrized suite is the guard: a core change that breaks either substrate fails CI |
| Cosmos real backend (emulator is amd64/Windows-heavy — see azure-servicebus rejection precedent) | Prefer a lightweight Cosmos-compat or keep the `azure_cosmos_core` as the Pro/Max backend if no viable emulator; document the choice |
