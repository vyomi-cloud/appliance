# Vyomi v2.8.1 — Tier exposure (completes v2.8.0)

**Goal:** make the v2.5.0–2.8.0 parity work actually *reachable* on every tier, not
just proven at the core level. v2.8.0 shipped the cores; this closes the wiring gaps
so they serve real traffic on the Nano relay, the Nano console backend, and the
Pro/Max appliance.

Status: ✅ COMPLETE · Shipped: v2.8.1 · Created 2026-07-13

---

## Gaps closed

### Gap 3 — `azure_sql` + `azure_iam` were test-proven but not live anywhere  ✅
Wired both into the shared `AwsWireRouter` with collision-free discriminators:
- **Azure SQL** → path prefix `/azure-sql/...` (stripped, delegated to `azure_sql_core`
  on the shared SqlStore; a bucket literally named `servers` still routes to S3).
- **Azure RBAC** → any path containing `microsoft.authorization` (→ `azure_iam_core`
  on the shared IAM store).
Because the router is shared, both are now live on the **Nano relay** AND the
**Pro/Max unified ingress**. Added to the relay CORES lists + the router conformance
test (permanent gate).

### Gap 2 — net-new services weren't on the DEFAULT Pro/Max path  ✅
The unified ingress is opt-in (its catch-all is greedy). Added
`wire_ingress.mount_new_services(app)` — **targeted, always-on, additive** routes for
the net-new services that have a *distinct path* and no legacy handler:
`/2015-03-31/functions` (Lambda), `/restapis` (API Gateway), `/azure-sql/...`
(Azure SQL), `/providers/Microsoft.Authorization/...` (Azure RBAC). Registered in
`server.py` BEFORE the S3 catch-all so they win, without a flag flip and without
disturbing existing handlers (verified with FastAPI TestClient; S3 catch-all
undisturbed). Header/Action-routed net-new services (EventBridge, VPC, Service Bus —
dispatched on `/` by X-Amz-Target/Action) can't be isolated additively and remain
served via the full unified ingress (opt-in).

### Gap 1 — Nano console  ◑ (backend readied; UI is follow-up)
- **Operation-depth on existing services** (SQS FIFO/DLQ, SNS filter policies,
  DynamoDB GSI, Firestore queries, KV crypto, KMS/Secrets rotation, S3 multipart,
  GCS resumable) is **already live in the Nano console** — those cores are loaded and
  the existing adapters pass through to them.
- The **net-new services** (Service Bus, EventBridge, Lambda, API Gateway, VPC,
  Azure SQL, Azure RBAC) are added to `nano-boot.js`'s CORES list so the console
  backend is in lock-step with the relay + build. They are **fully usable in Nano
  today via the relay**; dedicated *console UI pages* (routes.json + adapter op-
  functions + SPA pages) are a genuine UI feature, tracked as follow-up — not a
  wiring gap.
