# Vyomi v2.9.0 — Console data-plane integration

**Goal:** make the SPA/console *tightly integrated* with the v2.5.0–2.8.0 data planes
for all cloud providers — so the dashboard drives the REAL cores, not the generic
name-only catalog CRUD it used before.

Status: ◑ pt1 COMPLETE (backend + console REST API) · pt2 IN PROGRESS (SPA HTML forms)
· Created 2026-07-13

---

## pt1 — backend + console REST API  ✅ DONE (tested end-to-end)

The whole console dispatch chain — SW → `P.dispatch(provider, service, op)` →
provider handlers → adapter → core — now drives the real data planes:

- **`wasm/providers/dataplane_adapter.py`** — a thin console adapter over the real
  cores for all 7 net-new services (Lambda, API Gateway, VPC, EventBridge, Service
  Bus, Azure SQL, Azure RBAC). It **shares `aws_core_adapter`'s store singletons**, so
  cross-service flows work in the console exactly as over the wire:
  - EventBridge `PutEvents` delivers into the **console's** SQS queues.
  - API-Gateway `AWS_PROXY` invokes functions from the **console's** Lambda registry.
- **`aws.py` / `azure.py`** — `(service, op)` handler entries → adapter → cores.
- **`sw.js`** — REST path→tuple routes for every service + data-plane action
  (`/api/lambda/functions/{n}/invoke`, `/api/vpc/analyze`, `/api/azuresql/query`,
  `/api/azurerbac/check`, `/api/servicebus/.../receive`, `/api/eventbridge/put-event`, …).
- **`nano-boot.js`** loads `dataplane_adapter` before `aws`/`azure`.
- **`test_console_dataplane_adapter.py`** — permanently gates the full chain
  (registry→handlers→adapter→cores), incl. the cross-service flows. 44 host-green.

**Net effect:** the console's `/api/*` surface is now fully functional against the real
cores for all 7 services. `POST /api/lambda/functions/greet/invoke` runs the sandboxed
function; `POST /api/vpc/analyze` runs the reachability analyzer; etc.

## pt2 — SPA HTML forms  ▫ NEXT

The remaining layer is the dashboard UI (buttons/forms) that call the pt1 endpoints.
The console renders via `CATALOG.extras` schemas + `renderCrudStub` / `renderAnalyticsStub`
/ `renderConfigStub`, so the plan is:
1. Add `CATALOG.extras` entries for each new service (list/create via the proven CRUD
   stub system → low risk).
2. Add a **data-plane action panel** (a new render category) for the differentiated
   actions: Lambda **test-invoke**, VPC **reachability analyzer** form, API-GW
   **invoke**, EventBridge **put-event**, Service Bus **send/receive**, Azure SQL
   **query editor**, Azure RBAC **checkAccess** form.
3. Do it per-console (`aws-console.html`, `azure-console.html`) with browser
   verification (headless e2e) — these are large production files, so each change is
   verified before shipping rather than rushed.
